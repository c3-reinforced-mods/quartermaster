# Quartermaster - prototype plan (v1, 2026-09-27)

Quartermaster (formerly "Harmony") is a merge framework and in-game mod manager for Cossacks 3.
**Final descriptions, Workshop texts and branding are written only after the hands-on tests** - until then every user-facing text is a placeholder (a `TODO` mark). *Done 2026-09-30:* the texts are final; the marks are gone and a test keeps them out (`tests/test_m6_screens.py`).

Evidence base: ~40 in-game probe runs on 2026-09-27 and an engine API list (4857 declarations extracted from cossacks.exe) - both raw material outside the repository - and five write-ups of the findings (`docs/research/*.md`). Facts marked *verified* were observed in a probe; *inferred* ones must be confirmed in M0 before code depends on them.

---

## 1. Where the design stands

- **Go.** The core mechanism works end to end in probes: read pristine vanilla -> 3-way merge of two classic mods -> validate -> write into a mod folder -> restart -> engine runs the merged code natively and the MP checksum covers it.
- **It can be simpler.** About 25% of the previous design proves the core value (two classic mods changing the same `.inc` both work, no brick, in-game manager). The prototype is therefore split into **Phase A (minimal viable Quartermaster)** and **Phase B (full prototype features)**; B starts only after A's acceptance.
- Simplifications adopted from the design review (`docs/research/reviews.md`):

| Previous design | Now | Why |
|---|---|---|
| Separate `HarmonyOutput` mod | output inside Quartermaster's own folder | over-engineering + orphaned-output risk; Workshop folder keeps added files (verified) |
| Unit splitter (procedures/states) for `.inc` | plain 3-way line merge on `.inc`; record splitting only for data (Phase B) | all 313 vanilla `.inc` are one state each, 229 without procedures - "same state WARN" would flag everything |
| Full LCS table / Hirschberg | trim + Myers O(ND) with a D cap (parity-compact trace, (D+1)(D+2)/2 Integers <= 500k -> D <= 998, M0); over cap -> winner-takes-all FAIL | 4M-element arrays crash the game (verified); proven trim from probe 5; Myers verified in game in M0 (D=667 in 6 ms, [m0-probes](research/m0-probes.md)) |
| Raw-text IO for everything | raw-text IO with a size-aware reader for `.inc` as well as data and about.cfg; the engine parser only where it is lossless (own state files, lookups) - *revised 2026-09-28* | v1 chose the parser for `.inc` as "verified byte-identical"; the M2 in-game run showed it strips trailing spaces and appends to a Code node only once ([context §3](research/context-2026-09-27.md)) |
| ">50% changed -> replacement" by trimmed region | by edit count after the diff | the verified probe-5 case would otherwise be refused |
| Data merge, about.cfg, settings, create-mod, community rules in v1 | Phase B; community rules dropped from the prototype | not needed to prove the core |
| 3 fallback hooks | CameraControl + InitMinimap + DoProgress (drop DoAmbientSound) | InitMinimap has a second call path before DoInitialize (inferred -> M0) |

## 2. Safety decisions (binding for all milestones)

S1. **Output location.** Merged files are written into Quartermaster's own folder (`<QmDir>\data\...`). Rescue = disable Quartermaster in modman (one click, disables output too). mods.ini title: `Quartermaster`.

S2. **Never generated (winner-takes-all, listed in the report):** `scripts/lib/*.script`, `gui/menu.aix`, `gui/menu.cfg`, `gui/menu.inc/docreate.inc`, `scripts/dmscript.source`, `projects/project.main.prj`, `resources/resource.lib`, `scripts/resource.script`, `scripts/common.aix`, `scripts/common.inc/initmap.inc`, all other `.aix` machine files (units, progress, env, misc), `objects/objects.lib`, `*.prop`, `font*.lib`, `*.lng`, binaries. Verified bricks: libs, menu.aix, docreate.inc; the rest inferred (`docs/research/startup-chain.md`). Anything not on an explicit merge allow-list is winner-takes-all by default (**allow-list, not deny-list**). One exception, since the Workshop check of 2026-09-28 (the decision to build the pre-compile guard): Quartermaster *ships* `scripts/resource.script` - the installed game's file with the pre-compile guard after it, built by `tools/hbuild.py`, never written at runtime (S17). *Decided 2026-09-29:* global scripts without class or type declarations are to be merged and verified too (Phase C). This S2 rule stands until in-game probes prove the fallback: a merged library in Quartermaster's folder wins, and a start it breaks is undone by the guard before the libraries compile.

S3. **Merge allow-list.** Phase A: `.inc` files under `data/gui/menu.inc/` and `data/gui/common.inc/`, `data/scripts/**/*.inc` except S2 entries. Phase B adds data files with a record profile (objcustom.cfg, hotkeys.cfg, formations.cfg, wallcustom.cfg) and `dmscript.global` additive-only. *Revised 2026-09-29 (M9):* `dmscript.global` is **not** merged - it is a global script (S17): two enabled mods that ship it never load together, so there is no start in which a merged copy could be compiled; the winner's copy stays in effect and the report says why (planner reason `global-script`). The four data files are merged as planned.

S4. **Quartermaster ships no `dmscript.global`** (it is last in the order and would override other mods' globals). All runtime state lives in named parsers (`qm_rt`, `qm_val`, `qm_settings`; verified to survive map load) and files under `<save>\quartermaster\` (`GetAppSaveDirectoryPath`).

S5. **Hooks.** Primary CameraControl, second InitMinimap (runs through InitMap in both start-up DoCreates even when DoInitialize does not compile - M0), last resort DoProgress; plus EventMainMenu for the manager button (`cTagModManager`, `eventmainmenu.inc:154-156`). Hook lines: engine API only, no new globals, <= ~10 lines, byte-identical across generations except the generation/hash constants, once per process via a named-parser flag (verified to hold across a map load, M0), main menu only (InitMinimap also runs during skirmish map generation). Quartermaster **always merges its own hook lines** into these files (never winner-takes-all). The hook block goes before the first top-level Code line after any leading routine declarations (`cameracontrol.inc`: before `const cTagLeft = 20;`, verified in the M2 run; files without a leading routine: Code index 0), inserted after the merge by the same rule in the shipped static copy and in every generated file. A broken `eventmainmenu.inc` or `doprogress.inc` is not a start-up brick but kills the main-menu buttons or the menu tick for the session (M0), so both are written only after S7 validation, with the fallback tiers. Static hooked copies are shipped so a Workshop wipe loses merges but not hooks. Boot priority (M5): CameraControl; InitMinimap boots only from its 2nd call (its 1st, through InitMap, precedes CameraControl); DoProgress boots last and also runs the per-frame `qmTick` (restart, `booted` marker, UI Apply). All share the one `qm_rt` once-flag; the booting hook is logged. Report WARN when only a fallback hook ran. *Added 2026-09-29 (review of the host settings):* a fifth hook file, OnLanEvent (`onlanevent.inc`, the state `menu.cfg:26` names for LAN events): on a client, for a received parser (`gLanEvent = leParser`) with the number 7301, it runs `qmHostRecv` - where vanilla reads its own messages (`onlanevent.inc:176-215`). Believed until then that the main-menu tick could poll for the host's message; that sees only a frame's last message, and whether the engine keeps a parser selected outside its event is not known. Not a boot hook and not main-menu only: it runs per LAN event and costs one comparison on every other one. Like the others it is always merged, validated with the fallback tiers, and in the guard's list of hook files a later mod must not ship (S17).

S6. **Quartermaster's logic** lives in its own `.aix` files (`data/quartermaster/*.aix`) loaded at runtime into a trigger manager (outside the checksum); only version/generation/data-hash constants sit in the CameraControl hook (inside the checksum - verified that even an unused const changes it). *M4:* the generation constant is the content hash of all outputs, not a counter - a counter depends on each machine's history and would break the MP checksum between players with the same mods; the shipped copy carries the hash of a Quartermaster-alone generation, so a fresh install needs no restart.

S7. **Validation is mandatory before any write.** Candidate -> one-state validation copy in `<save>\quartermaster\val\` (outside the data mirror, so the engine never loads it natively) whose first line sets a named-parser flag and exits (S4 rules out a global flag); flag set = compiles. One validator trigger manager per boot is reloaded for every candidate: `StateMachineLoadFromFile` replaces its states, re-reads a rewritten path at once and recovers after a broken candidate (M0); never `TriggerManagerAdd` a live name (it creates a second, empty manager). Failure -> winner's file (fail-closed). Hook files fall back in tiers: merged+hook -> winner+hook -> vanilla+hook. *Revised 2026-09-30:* between the merged file and the winner's comes the subset - the merge without the mods that lost a conflict, when at least two mods stay (merged -> subset -> winner; merged+hook -> subset+hook -> winner+hook -> vanilla+hook). A mod's own changes can depend on each other: in game, Renaissance + MGraphics - Main Menu + Unofficial Patch gave a showmainmenu.inc that did not compile, because MGraphics lost the line declaring `const cmargin` and kept the lines using it; the old fallback then wrote Unofficial Patch's copy and lost Renaissance's main menu as well. The subset (Renaissance + Unofficial Patch) compiled and brought it back (run `ftB-withqm`). A written subset is `partial`, WARN, and the report names the mods left out; a mod whose own changes all went in (kept by the subset, or the winner whose copy was written) is OK for that file in the window.

S8. **Loop guards** (see startup-chain.md §guards): once per process; main menu only; no auto-restart while an MP sync is in progress (`StringRegister7<>''` or `<save>\mods.restore` exists - use `FileAge`, never `IsFileExists`); fingerprint = inputs only (canonical mod ids + enabled flags, other mods' stamps, vanilla FileAge, Quartermaster version; `ModLibraryGetData` gives no timeupdated, so a mod's stamp is a hash of path + FileAge over the scanned files it ships - M2); restart only if an output's bytes changed; mods.ini rewritten only if its content differs; start marker `<save>\quartermaster\state.cfg` (`gen, hash, written|booted, autoRestarts`); `written` without `booted` -> suspected brick -> do not regenerate the same hash, fall back, report FAIL; max 1 auto-restart per hash, 2 in a row. *M5 refinements:* the marker has three phases, written -> booting -> booted - the boot sets `booting` and the first main-menu frame (DoProgress `qmTick`) sets `booted`, so a start that died after the boot is also caught; `booting` found at the next boot -> suspected brick -> regenerate the same inputs winner-takes-all and report FAIL. Restart only when an output's content changed or the enabled order changed; refused (in this order) for MP sync, a SelfTest run (`<save>\qm_autotest.cfg` present, unless it holds `;restart`), a loop (the fingerprint moved across Quartermaster's own restart), two in a row, one per hash. *Revised 2026-10-01 (found in a manual run):* not a loop when only mods the engine registered at this start moved the fingerprint - the fingerprint without them is the marker's (`ref/index.py` known_fingerprint, `ref/boot.py` restart_plan). A folder made with New mod before an Apply restart is registered after Quartermaster at the next start; putting Quartermaster last again needs a restart, which the loop rule refused with a FAIL in the report. Two in a row and one per hash still bound the restarts. *Revised again 2026-10-01 (code review):* a mods.ini change that only moves Quartermaster past mods that ship none of its files and no file the index reads asks no restart at all (`ref/order.py` moved_past, needs_restart; qm_ini selfonly / over<j>): with no file in common their order decides nothing a restart would change. The New mod folder is such a mod; the loop rule's exception still covers a new mod that ships files. Outputs' FileAge stamps are kept, so outputs changed from outside (e.g. a Workshop update restoring the shipped copies) are detected as damaged and regenerated. Restart runs from `qmTick` >= 1.1 s after the last write, on a main-menu frame outside a map. At a normal boot `StringRegister7` is empty and `FileAge(<save>\mods.restore)` is -1 (M0).

S9. **Stale output cleanup.** Manifest `<QmDir>\data\quartermaster\state\manifest.cfg` lists every written file with its sources. Files no longer needed are deleted with `DeleteFileStream` (M0: works on relative and absolute mod-folder paths and on files the engine loaded at start; silent on a missing file) and the deletion is confirmed with `FileAge = -1`; if the file is still there it is overwritten with the current winner's file. Never `CopyFileStream`/`MoveFileStream` into a folder that may not exist (Copy raises and aborts the caller, M0); `RenameFileStream` does not replace an existing target.

S10. **Data (Phase B) is fail-closed.** Record merge with checks (unique keys, begin/end balance, record count, per-file bounds: formations <=160 records, objcustom arrays ExitPoints <=4, builders <=30, wall builders <=16, variation <24; hotkeys merged by Action with key-collision check). Failing data is not written -> winner's full file + FAIL. Report that a player's saved `Documents\cossacks\hotkeys\hotkeys.cfg` overrides the shipped one. *Revised 2026-09-29 (M9):* the fixed bounds above were vanilla's and would have refused the popular total conversions' own files (SvC, RoA and SvC++ raise `gc_formation_maxcount` to 203 / 332 / 329 and ship 50 shot points where vanilla has 40). A bound is now the constant in effect in the effective `dmscript.global`, or what one input already has, whichever is larger (twin `ref/records.py`); a merged file over it is refused (proof run m9b: 161 formations > 160, nothing written). Records are keyed by `Action` / `sid` / `WallVariation` / `id`; a record comes whole from the last mod that touched it (two mods changing different fields of one record are a conflict, not a field merge).

S11. **Order.** Phase A: canonical = Workshop id / local folder name, Quartermaster last. Phase B: dependencies from about.cfg, then the same tie-break. ~~No manual order in the prototype.~~ *Revised 2026-09-28 after the Phase A check:* the player sets the order by hand in the manager (up/down buttons and drag, if the engine allows dragging list items); Quartermaster stays last; the canonical order is only the default placement for mods Quartermaster has not seen before. The chosen order is kept by Quartermaster, written to mods.ini and is part of the fingerprint (it changes which mod wins). Same order in SP and MP is now the players' responsibility: a different order gives different merged files and a different MP checksum, and the report says so. *Revised again 2026-09-30:* the canonical order as the default placement was a mistake. It changed which mod wins every whole file two mods ship, so a set that starts without Quartermaster could stop starting with it. Cannons + State vs Country did exactly that (run ord-cannons-svc-qm: without Quartermaster the start compiles; with it the first boot sorted Cannons last and the next start stopped at "Error compiling scripts"). The default is now the order mods.ini has, which is what the game loads without Quartermaster, with Quartermaster moved last. Mods it has not placed follow the saved order in mods.ini's order. The canonical order is only what Auto-sort gives, and the window's custom-order footer is gone (it would show nearly always).

S12. **MP.** Quartermaster's hook lines change the checksum -> all players need Quartermaster (vanilla sync downloads it as a Workshop item). Deterministic output (fixed order, CRLF, no timestamps in generated files). Phase B adds a data fingerprint constant: content hash of merged data outputs + (relpath, winning mod id, Workshop timeupdated) of all overridden data paths (FileAge is machine-local and must not be used here). Note: `gstring_checksum` compares only 4 hex chars (16 bit). *Revised 2026-09-29 (M9):* no separate data constant. The merged data files are Quartermaster outputs, so their bytes are already in the generation's outputs hash, which is the CameraControl constant every player's checksum sees (M4). Workshop `timeupdated` is not readable from a script (M2), so it is not part of it: two players with different versions of a mod whose data file wins *unmerged* are told apart only by that file's own checksum, as in vanilla. *Added 2026-09-29:* settings of `host` scope (docs/authoring.md) - the host's Quartermaster sends its values in the LAN room (LanSendParser, message 7301, vanilla's numbers end at 300) and a client's takes them for the session; settings are not files, so the checksum does not see them either way. *Revised 2026-09-29 (review):* a client reads the message in the OnLanEvent hook (S5), takes only a value that fits its own copy's declaration, and never writes a host's value into its settings.cfg (qmSetSave).

S13. **New mods.** The engine registers and enables every new folder in `mods\` before Quartermaster runs (verified, also folders without mod.ini; M0: appended at the end of mods.ini with `dis = False`, existing entries untouched). Quartermaster marks them "new" in the manager and includes them in the next generation; it does not try to prevent their first run. **Revised 2026-09-28 (the pre-compile guard, S17):** believed until then that nothing of Quartermaster runs before a new mod's first run; what it cost: a new subscription that ships a clashing library stopped a test start at "Error compiling scripts" with no word from Quartermaster. True: the on-load script runs before the libraries compile and can take a mod out of the start (docs/research/guard-probes.md); new mods with a global-script clash are now switched off there (S17). Other new mods still load on their first run.

S14. **Limits.** Per state: <=1M Integers per array, String pools <= ~200k (String arrays cost ~ 4.6 us per element on every state call; 1M took 15 s), files > 60k lines or D > 998 -> winner-takes-all WARN. `Chr` never used (does not compile) - char table + `~NNN` escapes. Not in the dialect (M0): open arrays, `High`/`Length`/`SetLength`, and state-level nested functions returning `String` (return through a `var` parameter). Integer arithmetic wraps, `shr` is logical, `and`/`or` short-circuit. Named-parser keys are case-folded and trimmed: only identifier-like keys; line interning uses an own hash table. Case-insensitive identifier uniqueness enforced by the build lint.

S15. **Test safety.** In-game runs only while nobody else uses the machine; lock file `Documents\cossacks\swfp_game.lock` (shared with SWFP sessions); mods.ini backed up/restored byte-identical; fixture mods live OUTSIDE `mods\` and are copied in only for a run, then removed; after every run `harness.py sweep`-style check that the game folder is untouched and no stray folder is left in `mods\`; never write into vanilla `data\`.

S16. **Names and texts.** Project and mod name **Quartermaster** (mods folder `mods\Quartermaster`, about.cfg id `quartermaster`, GitHub `pjugowiec/cossacks3-quartermaster` - publicly free on 2026-09-27; C3 Workshop: 0 items named Quartermaster/Harmony/Hetman). "Harmony" was rejected as misleading (the well-known .NET patching library: 3292 RimWorld / 451 Bannerlord Workshop items), "Hetman" because it is a Ukrainian cavalry unit in the game (`country.script:1984`). Note: vanilla has a "quartermaster" adviser service (`bquartermaster`, `classes.script:3488`; PL text "usług kwatermistrza", `locale/pl/new.txt:235`) -> never use a bare `quartermaster` identifier; code prefix `qm` (no vanilla identifier starts with `qm`), strings `qm_*`, log marker `[qm]`. All user texts were placeholders until the hands-on tests. *Revised 2026-09-29:* the final English and Polish texts and the translations into every language the game ships are written in the project, and EN and PL are read through by hand before release. They live in a locale table of Quartermaster's own, not in the game's files. Repo language English; commits `<type>: <imperative>`.

S17. **Global scripts and the pre-compile guard** (decided 2026-09-28, docs/research/guard-probes.md; twin `ref/guard.py`). A mod's global scripts are its `scripts/lib/*.script` and `scripts/dmscript.global` / `.source`; two enabled mods that ship the same one cannot both load (the later copy replaces the whole file; usually "Error compiling scripts"). (a) The guard, in Quartermaster's `scripts/resource.script` after the vanilla code, engine natives only: a *new* mod (not in known.cfg) whose global script an enabled mod already ships is taken out of the running start with `SteamSyncWorkshopItems` and switched off in mods.ini (kept as loaded otherwise), a note is written and the game restarts; never in an MP sync, never on a game whose resource.script changed, never twice for the same mods. *Corrected 2026-10-02:* "changed" was told by the file's FileAge until 0.1.2, but FileAge is the day Steam wrote the file on that machine (every vanilla file of the author's installation reads 2026-08-24, the copy on a second computer 2026-09-19), so the guard was off - `game-version` - on every installation but the author's; the first start on a second computer showed it. It compares the file's content now: the installed resource.script read by its absolute path and hashed as `qhash` (`ref/guard.py` game_stamp). The guard also moves Quartermaster's entry to the end of mods.ini (and restarts) when an enabled mod after it ships one of its hook files - new subscriptions are appended after it, and one that replaces the DoProgress hook left Quartermaster without its tick, restart or notice (proof run p4 of 2026-09-28). (b) The boot lists every clash between enabled mods in the report and the window marks those rows, ~~FAIL~~ WARN since 0.1.3. (c) ~~The manager's Apply refuses a pending set with a clash.~~ The manager's Apply asks before it writes a pending set with a clash: a `Note:` line in its dialog (0.1.3, below). (d) After a guard restart the window opens once with the list of mods switched off. Known limits: names only - a clash that would compile is refused too, one that is not a shared file is not seen; mods enabled outside Quartermaster with a clash between known mods still stop the game (the Mod Manager is the rescue, S1). *Corrected 2026-10-02, revised 2026-10-03 (0.1.3):* that last limit is gone. It was believed that only a new subscription needs the guard - a known mod being one the player had chosen; what it cost: the owner switched 32 known Workshop mods on in modman at once (State vs Country and its ++, Rise of America and its +, 19th Century and more, the same libraries), the guard logged `clean` and two starts in a row stopped at "Error compiling scripts". The first fix (2026-10-02, pushed but never on the Workshop) judged in advance, by names, every enabled mod outside the set of the last start that booted. What it would have cost, found before the upload: names cannot tell a pair that stops from a pair that runs (an add-on built on another mod ships that mod's libraries on purpose), so such an add-on would have been switched off at every start and refused by the window, with no way out but switching Quartermaster off. True now: the guard reacts to a start that stopped instead of predicting one. ~~An ordinary start judges new subscriptions only, as in (a).~~ An ordinary start judges, softly, every mod outside the last set that booted (revised again the same day, below). A start that stopped is proven by two facts together: the guard's record of it (`compile.cfg`, written with `pending = 1` before the libraries compile, set to 0 by the boot) is still pending, and that start's log (the second newest `cos_*.log` by FileAge) has the engine's `CompileFramework() - compile global script error` line, which no start that compiled writes (on the author's machine 22 of 1268 logs have the word, every time in that error). After one, the guard steps back towards the last set that booted - `<save>\quartermaster\compiled.cfg`, written by the boot (qmGlobals, never on an Apply or in an MP sync) when the enabled mods differ from it - one step per start: `failed-names` switches off the mods outside that set whose global script another enabled mod already ships, judged as (a) judges a new one; with none, `failed-revert` switches off every mod outside it; when every enabled mod is in it (a Workshop update broke a set that booted) or there is no record, `failed-vanilla` switches off every mod but Quartermaster, since the game alone compiles. Each step restarts the game; that start's log has no `CompileFramework` line, so the start after it is an ordinary one, and the next step comes only if it stops again. The note's `why` names the step, the window's notice says the last start stopped and lists the mods switched off, and the guard's last log line says what it judged by (`basis=compiled|known|none|-`). Limits of the design: the player sees "Error compiling scripts" once (at worst three times, one per step) before a later start mends it - only judging in advance avoids that; the MP sync and a game whose resource.script changed stay outside the guard, as above; the guard makes sure the game starts, not that a set plays well. *Revised again 2026-10-03 (0.1.3, four changes before the Workshop upload):* it was believed that reacting is enough - one "Error compiling scripts", then the steps mend it. What it cost: the owner's test of 0.1.2 from the Workshop (starts of 2026-10-03 08:45 and 08:46, (e) below) ran into the engine's dialog twice in a row, and the dialog cannot be helped once a set reaches the compile: its text is two string constants in cossacks.exe, next to `data\projects\project.main.prj` (checked 2026-10-03), so no mod can change or hide it; the only way round it is not to let a set that would fail reach the compile. True now: (1) an ordinary start judges in advance again, softly: every enabled mod outside the last set that booted (compiled.cfg) and outside the set the player last applied in the window (chosen.cfg) is judged by names as (a) judges a new subscription - switched off before the compile when an enabled mod already ships one of its global scripts, then the game restarts; the note's `why` is `conflict`, and the notice says the mods have not started together before and that with both the game may stop. Mods that booted together (in compiled.cfg) are trusted. Without compiled.cfg (the first start of 0.1.3) known.cfg is the basis, as in 0.1.2: new subscriptions only. The way out the first 0.1.3 lacked is the window: a pair that does work together (an add-on built on another mod) is activated there, and the Apply writes `<save>\quartermaster\chosen.cfg` (`d<k>` the dirs of every mod the applied mods.ini enables, in load order, `n`), which the guard trusts at the next start; the boot (qmGlobals, never on an Apply or in an MP sync) clears it to `n = 0`, so the pair gets one start and is in compiled.cfg from then on - and when that start stops, the steps undo it and the guard clears chosen.cfg itself. (2) The steps run only while the set that stopped is still the one enabled: compile.cfg's dirs against the enabled mods now, as a set (the order may differ; Quartermaster's move last is no change); otherwise the start is an ordinary one. The engine's dialog itself says "Try to disable some mods via Mod Manager", so a player often switches the culprit off in modman and starts again, and the steps would then have switched off more than needed; the same test covers a guard restart without Steam (SteamSyncWorkshopItems did not run, so the mods it switched off were still compiled in that life, and mods.ini has them off already). (3) A second log mark: `Compile script error: DoCreate` (the main menu's DoCreate did not compile; nothing runs after it) proves a start that stopped as the `CompileFramework` line does. Of the 1268 logs on the author's machine (2026-10-03) 19 hold it, none of them reached the main menu (no `...DoCreate started...` line), 8 also have `CompileFramework`; `Parser load error` is in 18 logs that did reach the menu, so it is not used. (4) A compile.cfg written by 0.1.2 has no `pending` key and counts as pending - with (2) and the log mark that is still safe - so the first 0.1.3 start after an update from 0.1.2 with a set that already fails steps back instead of failing once more (`ref/guard.py` failed, same_set, log_failed, decide). The limit above - "Error compiling scripts" seen once before a later start mends it - now holds only for a failure no file name shows (a broken mod, an update that breaks a set, a clash in another file): the engine's dialog once, then the steps undo it. Screens: Quartermaster cannot add states to menu.aix. M0 chose mechanism (a): its screens are GUI states added at run time with `StateMachineStateAdd`/`AddCodeLine` from code lines read through the parser; the engine dispatches real clicks to them, and ListBox tab columns, the InputBox and select events work. Loading a skirmish drops them, so the CameraControl hook re-adds missing states (and re-creates Quartermaster's trigger manager, which dies at every InitMap and map load) on every DoCreate. Mechanism (b) - a vanilla Event state forwarding a tag range to a trigger manager - is not used: a trigger-manager state cannot read the GUI event values ([m0-probes](research/m0-probes.md), probes 9-10).

### Dev side (Quartermaster developers only - never mod authors or players)
- `tools/hbuild.py`: assembles `.aix`/`.inc` from `src/**/*.pas` (SWFP `emit.py`-style templates), inlines helpers per state (each state compiles alone; procedures in `.inc` are file-local), wraps `[*] = ;` lines and doubles quotes, lints (vendored `c3kit/formats/gscript.py`, duplicate identifiers case-insensitive, no `Chr(`, array budgets), generates `vanilla.idx` from the installed game, writes `dist/Quartermaster`, `--deploy` copies to `mods\Quartermaster` (the only writer into `mods\`); `--update` puts a new build into it and keeps its `mod.ini` byte for byte (after an upload through the game's Mod Manager that file names the Workshop item; `--undeploy` then `--deploy` would make the next upload a second item), and removes every file the build does not have, so the outputs the game wrote there never go up with an upload.
- `ref/`: Python reference of text IO (including the EOF quirk), diff, merge, classifier, records, about.cfg, order - cross-checks in-game results.
- `tools/hrun.py`: in-game harness generalised from the launcher used for the probe runs (+ journal and `--recover`).
- `tools/fixtures.py`: builds test mods outside `mods\`.

### Runtime flow (every start)
Hook (once, main menu) -> load `core.aix` -> Boot: read state marker -> guards -> mod list -> load order (mods.ini's own or the saved one, S11) -> ensure Quartermaster last (rewrite mods.ini only if different) -> index (the stamps need it) -> fingerprint -> unchanged? stop : plan -> per merge path: read vanilla (absolute path) + participants -> diff/merge/classify -> validate -> write -> cleanup stale -> manifest + report + marker `written` -> restart (vanilla way) -> next start: marker `booted`.
