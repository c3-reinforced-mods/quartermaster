# Quartermaster (formerly "Harmony", then "Quartermaster") - full context for the design analysis (2026-09-27)

Project name is now **Quartermaster**. Final descriptions / Workshop texts are NOT to be written yet (hands-on tests first) - use placeholders.

Game dir: `C:\Program Files (x86)\Steam\steamapps\common\Cossacks 3` (paths below relative to it).
Engine script API: 4857 declarations extracted from cossacks.exe.
Probe generators, the launcher and the logs of ~40 in-game runs are raw material outside the repository; probes are referred to by number (probe 5, probe 9, ...).
Reference mod with a working WASD camera + test harness: `mods\SW_Frontline_Protocol` (git repo, Python build pipeline: `tools/build.py`, `tools/autotest.py`, `tools/swfp/patches/camera.py`, `tools/swfp/templates/*.pas`).

## 1. Problem and goal
A Cossacks 3 mod is `mods/<mod>/data/...` overriding WHOLE vanilla files (overlay). Two mods changing the same file: the last one in `mods/mods.ini` wins, the other silently breaks. The in-menu "Mod manager" button only opens the Workshop URL (`data/gui/menu.inc/eventmainmenu.inc:154-156`).
Quartermaster = (1) merge changes of several mods in the same files; (2) an in-game mod manager like RimWorld (left: installed, right: active with statuses, auto-sort, validation).

## 2. Constraints
Player runs nothing extra (normal Steam start). DLL/exe patching allowed if needed - current design needs none. ~~Manual order in modman must not matter (Quartermaster decides).~~ *Corrected 2026-09-30 (docs/plan.md S11):* Quartermaster deciding the order - canonical by default - changed which mod wins whole files and bricked a set that starts without it (Cannons + State vs Country). The order mods.ini has is now kept, Quartermaster last, until the player sets one in the manager (docs/plan.md S11). Mod authors: no Python/CLI (templates + in-game buttons). Keys/types in English, list separator `;`. Quartermaster public (MIT).

Mod list / overlay

- **A subscription is not registered while a local folder's mod.ini names it** (2026-10-02, harness runs `wsclaim1` and `wsplain1`, Quartermaster not deployed, ZoomOut (873048118) left out of mods.ini). With a folder in `mods\` whose mod.ini says `publishedfileid = 873048118`, the start did not add ZoomOut (`wsclaim1` mods.ini.during: the folder at :188, no row for the item); the same folder with `publishedfileid = 0` and ZoomOut was added after it with `dis = False` (`wsplain1` mods.ini.during:188-193). Found when the published Quartermaster (3811537510) never loaded from the Workshop on the author's machine: the game's Mod Manager writes the item's number into the local folder it uploaded from (`mods\Quartermaster\mod.ini:2`), and the subscribed copy in `workshop\content\333420\3811537510` stayed out of mods.ini through three starts (2026-10-01). So a subscribed item loads only once its uploading folder has left `mods\` (or names no item); the folder must come back to publish an update, or the next upload makes a new item.
- **A String variable handed to a script procedure both by value (`const` or plain) and as a `var` parameter comes back damaged** (2026-09-29, in-game run `rqprobe-133004` and the instrumented run after it): `qmLowerAscii(qmAbRid, qmAbRid)` - the output cleared, then the input read - turned `qmtestverbase` into `qmtestverbas`, `abcdefghijk` into `abcd`, `abcdefghijklm` into `abcdefghijkl`, when the variable had last been written through a `var` parameter; right after that write it still read right, and a plain assignment before the call hid it. The tests' interpreter kept the two apart, so only the game showed it. Never pass one variable both ways; `tools/hbuild.py` refuses it (`gscript-alias`) and the interpreter raises. StrPos and SubStr themselves are 1-based and right (in-game run `strpos-132814`).
- **The game's language and its texts' encoding** (read from the installed files, 2026-09-29). `data\scripts\resource.script:1-33` takes the Steam UI language (`SteamwrapGetSteamUILanguage`; `english` without Steam) and copies that language's block of `data\locale\lang.loc` (`FontsCollectionFileName`, `LocaleTableFileName`, `LocaleTableListFileName`) into `<save>\resource.lib`, which the game loads (this machine: `.\data\locale\pl\table.lng`). There are 11 languages: english, french, german, czech, polish, russian, italian, spanish, ukrainian, portuguese, turkish (folders en fr de cs pl ru it es uk po tu; `lang.loc` also has a `default`, the English one). The font follows the language: `font1250.lib` for cs and pl, `font1251.lib` for ru and uk, `font1254.lib` for tu, `font1252.lib` for the rest. The locale texts are single-byte code pages, not UTF-8. `pl\gui.txt` / `gui.lng` do not decode as UTF-8, and `\xaf ywno \x9c \xe6` is "Żywność" in cp1250 (`pl\gui.lng`, the first records). A `.lng` is u32 record count, then per record u32 length, `key=value`, and 0x03 (`pl\gui.lng`: count 0x1cc, first record 24 bytes). So a text Quartermaster shows in a language needs that language's code page. *Shown in the game, 2026-09-29 (run `c0c6-text-180415` and its screenshot):* two mods named "Zażółć gęślą jaźń" in their about.cfg, in Quartermaster's window of the Polish game: the cp1250 name reads right, the UTF-8 one shows as its bytes read as cp1250 ("ZaĹĽĂłĹ‚Ä‡ gÄ™Ĺ›lÄ…"). Text is drawn byte for byte in the language's code page; nothing converts UTF-8.
- **Global scripts merged into a later mod's copy** (Phase C probes, 2026-09-29, runs `c0c1-*`, `c0c5-valid-180214`). A local mod loaded last whose `data\scripts\lib\<name>.script` is two mods' copies merged line by line against vanilla replaces both, compiles, and the start reaches the menu: State vs Country + MGraphics - Lights (`miscext2.script`, a marker line at its end logged, `c0c1-misc2-180131` 0.log:33), State vs Country + Cannons (`unit.script`: SvC's file with Cannons' two value changes, one of them on a line SvC changes too, `c0c1-unit-180145` 0.log:21) - a pair whose start fails without it ([guard probes](guard-probes.md), verdict 4) - and Patrol + State vs Country (`dmscript.global`). The libraries compile as one text: a line that is not Pascal at the end of `miscext2.script` fails as `CompileFramework() - compile global script error: Syntax error: Line: 60812` (`c0c2-broken-175706` 0.log:6). The validation copy (a state, [M0](m0-probes.md)) is not enough to accept a merged library: with State vs Country's libraries loaded it compiles every merged file and fails the broken one, but it also compiles Cannons' own `unit.script` - the copy whose start with State vs Country fails with `Unknown Name` - because what it cannot see is a name the other libraries use and the candidate no longer declares. A merged library must keep every name either side declares (checked on the text before the validation copy); `sound.script` declares classes, which the validation copy cannot compile at all (section 3, classes.script).
- **The line number of a `CompileFramework` error, and which `dmscript.source` the compile uses** (2026-09-30, probe runs `lines-*`). The libraries compile as one text in the order of the `Files` list of the vanilla `data\scripts\dmscript.source`, after its 67 `Code` lines: a line that is not Pascal put first in classes.script is `Line: 69`, first in parser.script (the second library) `Line: 8193` - one more line per file boundary, each library counted by its own lines (the copy that wins, a mod's or vanilla's). Further on the numbers drift a little from that sum (unit.script +5, miscext2 +13, miscext3 +14 over 62 923 lines; not lone CRs, other control bytes or long lines - cause unknown), so the rule finds the library and its line to within about fifteen. On a real failure it did: Renaissance then Cannons stopped at `Line: 39434, Column: 13: Unknown Name`; the rule over vanilla's dmscript.source gives Renaissance's player.script line 1429, and its line 1420 column 13 is the first use of `_unit_orderattackext`, which Cannons' unit.script does not declare. Over Renaissance's own dmscript.source (77 Code lines, 30 libraries) the same rule is 283 lines off: **a mod's copy of dmscript.source is not what the compile uses** (compare the startup chain, where its Code did not log), so Renaissance's extra libraries miscext4.script and miscextfow.script, listed only there, are most likely not compiled - not checked.
- **For a folder without mod.ini, `ModLibraryGetData` does not write the title, `last` and the other mod.ini fields**; `dir` and `dis` are written. Read in a loop into the same variables, such a row carries the previous row's title. Reset them before each call. Evidence: run b4 of 2026-09-29 (runs `b4-*`), folders QMTestNeeds / QMTestTC1 / QMTestTC2 with only an about.cfg, and the report named all three `QMTestConflict`, the mod of the row before.
- **A start can come up without its scripts, now and then** (seen twice: life 1 of the first try of proof run p4, `proof-p4-all-new-204707`, 2026-09-28; life 2, after Quartermaster's restart, of `proofB-p6-known-clash-105152`, 2026-09-29): the log says `FileStreamExists: .\data\scripts\dmscript.global` right after `LoadFromStreamProject end` and then GUI errors - in p6 `Compile script error` for OnClear, DoCreate and OnMouseMove, the project load over in 2 s instead of the usual 20-30 s - and the game does not get to its menu. The same mods with the same Quartermaster files started normally in the next try (p6: the same generation, outputs hash 1461688-2030185-316, in `proof-p6-known-clash-213636` before and `proofB-p6-known-clash-110450` after). *Narrowed the same day (runs `m12f*`):* 5 of 12 starts between 11:41 and 11:47 failed exactly so - one of them `m12fvanilla`, the game with no Quartermaster at all - while the test suite ran in another process and read the game's own files (vanilla `data\` files, `dmscript.global` among them); the starts after it did not. The earlier p6 failure fell into a test run too. So the cause lies outside Quartermaster, and another process reading the game folder while the game starts is the likely trigger (the error is the engine failing to open `dmscript.global`). For test runs: nothing else reads the game folder while a run starts. For a player: starting the game again is the way out.
- Same file in two mods: last in mods.ini wins (engine files and `.\data\` overlay paths).
- Rewriting mods.ini from script (parser, path `ModLibraryGetIniFile`) + restart: honored, not overwritten.
- Script cannot list directories (`ParserGetFilesInRoot`, `RefreshFileList` return files only; no `*` in dir part). Known path check works. `FileAge` = DOS date (2 s), changes on write; missing file = -1 without log ERROR.

Runtime code
- `TriggerManagerAdd` + `StateMachineLoadFromFile` + `StateMachineExecuteState`: works in menu and battle, synchronous, shared registers, globals/libs visible. Map load wipes trigger managers.
- Runtime-loaded code NOT in MP checksum (`StateMachineLibraryCodeMD5Checksum`, `data/scripts/lib/init.script:161`). `.inc` changes DO change it (incl. an UNUSED const in `cameracontrol.inc`, verified with identical other files). **Data (objcustom.cfg) is NOT in the checksum** (vanilla hole).

Patching by files (main mechanism)
- Pristine vanilla despite overlay: absolute path `ExtractFilePath(GetApplicationFileName)+'data\...'`.
- Parser round-trips single-section `.inc` byte-identical (`Code` node, values with leading `;`; write by index `ParserSelectByHandle`+`ParserSetValueByIndex`, append key `[*]`; `ParserClearByHandle` on Code breaks structure). Parser is LOSSY on data files (multi-section .lib, comments, structs) -> merge data as raw text.
  **Corrected 2026-09-28 (M2 in-game run m2a).** Believed: the round trip is byte-identical for every `.inc` and `[*]` appends any number of values. It had been verified on single files only (cameracontrol.inc, one append). True instead: the parser strips trailing spaces from Code values (13 vanilla `.inc`, 39 values), so a parser read of those files is lossy; appending with key `[*]` works once - every further append overwrites the child the first one created (3 appends to oncamera.inc left 74 values, the last being the third append); the engine writes a Code node with 1 value as `Code[*] = v` and with >= 2 values as a struct, whatever the input form; a Code-less file given a `Code` child is written as `Code.[*] = ...`, not a Code node. *Added 2026-09-28 (M4 runs m4a/m4c):* on load the parser also drops a value's leading spaces (the saved file keeps them; 34 of 72 report values starting with spaces read back without them) - a value guarded by a leading `;` keeps its spaces, as Code values do. Cost: the plan's "parser for `.inc`" simplification (plan §1) is revised - `.inc` files are now read and written with the raw 4-byte IO.
- Raw text: `FileStreamReadInteger/WriteInteger` 4 bytes LE; past EOF returns remainder then constant 32, no exception; writing creates missing subfolders.
  **Corrected 2026-09-28 (M2 in-game run m2a).** Believed: past EOF the reader returns the constant 32. True instead: it returns a stale value (4 after files of whole integers; an unrelated value on the first read of an empty file), so every file whose length is a multiple of 4 gained a junk last line. The 32 seen in probe 6 was not a constant. Cost: the EOF quirk modelled in the Python reference was wrong; the reader must stop at the file's known size (from `vanilla.idx` or Quartermaster's own writer). **`Chr` does not compile at all** -> char table `SubStr(tbl,b-31,1)` + internal `~NNN` escapes; `Ord(SubStr(..))` works. 1.5 MB read in 1.7 s. No file-length API.
- Write into a mod folder + restart the vanilla way (`LanShutdown; SteamwrapFree; RestartApplicationParam('')`, `data/gui/menu.inc/onworkshopautoupdate.inc:4-11`) -> engine loads generated file natively, checksum covers it; also `.script` libs. Restart 25-95 s.
- 3-way merge in script (LCS lines vs vanilla): two classic mods with full oncamera.inc -> 5 hunks, 1 conflict detected, 16-47 ms; after restart both changes ran.
- Pascal is case-insensitive (array `M` + var `m` = "Compile script error" without detail).
- **Local arrays: 1M Integer OK, 1M String OK (15 s alloc), 4M Integer CRASHES the whole game.**
In-memory / hot reload
- `StateMachineStateAdd/AddCodeLine` append only; compiled state needs `StateMachineLibraryFlush`. GUI machine reloads from disk on map load. `StateMachineReloadGUI` only for files present at start (+1 exception); `NeedRestartGUI` does not refresh content; `StateMachineReloadLibrary` throws. -> always restart.
Validation and failures
- State copy with first line `gint_ok := N; exit;` in a separate trigger manager: flag set = compiles; broken -> flag 0. `type..class`, `record`, `global`, `const` compile in such wrapper. Procedure-only libs validate (init, unit 12k lines 0.34 s, country); classes.script does not (cause unknown). *Corrected 2026-09-29 (probe run `cls-111839`):* the cause is known now. A class type whose name is already declared - by the classes.script the game loaded - cannot be declared again in a state: all 122 `type X = class` units of vanilla classes.script fail in the wrapper one by one, as does `type TColor = class` alone, while a class with a new name compiles, and its 281 consts, 96 globals and 2 procedures - vanilla names too - compile. So a global script that declares classes cannot be checked in a running game; one without class declarations can, against the global scripts loaded at the time.

## 4. Current design (after three design reviews) - "safe" decisions
- Quartermaster = Workshop mod; **merge output lives inside Quartermaster's own folder** (separate HarmonyOutput dropped: over-engineering + orphaned-output risk; file persistence in Workshop folder verified; if a Quartermaster update wipes output -> regenerate + one restart). Disabling Quartermaster in modman disables output too = one-click rescue. Title placeholder: "Quartermaster - disable if the game misbehaves".
- Quartermaster moves itself to the END of mods.ini on every start.
- **Never generated (winner-takes-all):** `lib/*.script`, `menu.aix`, `docreate.inc` (bricks), `dmscript.source` (unused from mods). `dmscript.global`: additive-only merge (new `name = Type` lines, unique names), anything else winner-takes-all.
- **Quartermaster start hooks:** CameraControl (primary) + fallbacks (DoProgress; InitMinimap/DoAmbientSound) - Quartermaster ALWAYS merges its own hook lines into these files (never winner-takes-all); report WARN when only a fallback ran. Data hash constant carried in CameraControl hook lines (verified: changes checksum). Hash of all active data ALWAYS (Quartermaster already changes checksum by its hook lines, so compatibility with non-Quartermaster players is impossible anyway; vanilla sync downloads Quartermaster).
- Merge scope: `.inc` + data files only. ~~Canonical order only (dependencies, about.cfg hints, community rules, then mod id) in SP and MP; no manual order in prototype; first-run notice about changed asset winners.~~ *Corrected twice (docs/plan.md S11):* a manual order in the manager since 2026-09-28; since 2026-09-30 mods.ini's own order when the player set none, so no asset winner changes at the first run; the canonical order is what Auto-sort gives.
- Index per mod: files in 259 known vanilla dirs + `extraDirs`; cache via Workshop `timeupdated` / local `FileAge`. Only files touched by >=2 mods are read.
- Split into units (procedure / record `sid` / state) -> hash compare -> diff only changed units; **diff algorithm with linear memory (Myers linear-space / Hirschberg), no full LCS table**; patience anchors for big regions. Uncertain split -> one unit + WARN. Entry gate: split of all 524 vanilla files re-joins byte-identical.
- Classification: same line -> conflict (later wins); same procedure/state -> WARN "logic unverified" (silenced by `compatibleWith`); else OK. Normalize for compare (BOM, trailing ws, tabs, CR), write CRLF; >50% changed -> treat as full replacement.
- Data merged per record with checks (unique keys, begin/end balance, record count vs vanilla); **fail-closed: data failing checks is NOT written** -> winner's full file + FAIL.
- Validation of every generated state via flag wrapper before writing. Start marker (generation N) + merge report text file. Always restart (no hot reload).
- Manager: left installed (all mods.ini entries incl. auto-registered; marks Local / Workshop / Local copy of Workshop mod; newly registered = "new", engine auto-enables them -> Quartermaster applies its policy), right active with FAIL/WARN/OK; validation on "-> activate" and "Apply" (deps, declarations: key collisions with hotkeys.cfg & other mods, duplicate ids; trial merge; trial compile; optional mod `validate.aix`). Modman remains the rescue.
- `about.cfg` v1 (optional, own raw reader): `key = value`, lists `;`, options `|`, range `..`, `#` comments. Keys: id, name, version, quartermaster (min version), gameBuild, type (mod|totalConversion|library), exclusive (camera, ai, ui, balance, economy, sound, graphics, hotkeys), extends, requires (id>=ver), loadAfter, loadBefore, incompatibleWith, compatibleWith, setting (`id;type;default;label[;extra][;scope]`, types bool/int/float/key/choice/text, scope local only in prototype), extraDirs. Everything else derived.
- Mod settings screen from declarations; values in a file under Documents\cossacks + named parser (survives map load); change applies without restart.
- "Create mod" form -> folder with mod.ini + about.cfg + data\ (game registers it); "Edit game file" copies a vanilla file; "Create about.cfg" draft for existing mod. Publishing via modman.
